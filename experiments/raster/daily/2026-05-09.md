## Handoff for next session

**The real bug**: The LDS-relief refactor (Tests 71-72) moved `warpEmitMask`
and `warpEmitPrefixSum` out of LDS into a per-block global allocation
(`CoarseGlobalScratch`). Address calculation `&s_warpEmitMask[threadIdx.y][lox + (loy << CR_BIN_LOG2)]`
appears to be in-bounds by my analysis — values clamp to [0, 255], and
the buffer is sized for `numImages * numCoarseBlocks * sizeof(CoarseGlobalScratch)`.
But on the first WRITE to that address, the GPU faults with
`hipErrorIllegalAddress`. Reading it (Test 112's currPtr computation
without dereference) is fine.

**What's known to work** (Test 91 pattern):
- Real coarse impl with early `return;` after `atomicMax(dbg, 1)` — kernel launches and runs the marker.
- Real coarse impl up through the AABB calc + `U8 *currPtr = ...` + `(void)currPtr;` + `return;` (Test 112) — kernel launches, reaches the end, exits cleanly.

**What faults**:
- Adding `*(U32 *)currPtr = maskBit;` (atomic OR non-atomic) — fault.

**Next session attack plan**:

1. Run again and compute `currPtr` actual numeric value via a kernel write
   to host-pinned memory (don't use `*currPtr` — instead, write `(uintptr_t)currPtr`
   to a known-good buffer like `p.debugTrace[1]`). Compare with `p.warpEmitGlobal`
   bounds: `[base, base + numImages * numCoarseBlocks * sizeof(CoarseGlobalScratch))`.
2. Print `lox`, `loy`, `threadIdx.y`, `blockIdx.x`, `blockIdx.z` for the
   threads that fault — there must be a value combo that escapes the buffer.
3. Audit `RasterImpl.cpp` setupParams: when does `m_warpEmitGlobal.reset()`
   run vs when does `p.warpEmitGlobal = m_warpEmitGlobal.getPtr()` get
   set? If the buffer is reallocated between setup and dispatch, the
   pointer is stale.
4. Compare `CoarseGlobalScratch` layout (struct order, padding) against
   the kernel's pointer arithmetic: does `gscratch->warpEmitMask` start
   exactly where the kernel expects? Check sizeof and offsetof.
5. Consider reverting the LDS-relief refactor and going back to LDS-resident
   `warpEmitMask`. With `CR_COARSE_WARPS=4`, FineSmem fits in 32 KB
   without the global scratch buffer.

## Key milestones today

### The stale-binary trap (Tests 55-59 retracted)

Adding a `printf` to `coarseRasterImpl` forced a recompile that the
prior `pip install .` cycles had been silently skipping. After the real
recompile, ctor output flipped from `coarseBlocks=4 fineBlocks=3` to
`coarseBlocks=1 fineBlocks=1` and the harness crashed immediately.
Tests 55-59 were running stale 32 KB + no-op binaries despite source
saying 48 KB + real impls. See [findings.md § stale-binary trap](../findings.md#stale-binary-trap-operational).

`run.sh` now performs the mandatory rebuild protocol every run.

### The VSCode auto-revert trap (Tests 65, 67)

VSCode kept Constants.hpp open in a tab. sed-edits to the file got
overwritten by VSCode's in-memory buffer on auto-save before the
build kicked off. Test 65 crashed the GPU + Xorg as a result.
Test 67 was the layered-defense pass — three guard layers in `run.sh`
caught the mismatch before the harness launched. See
[findings.md § VSCode auto-revert](../findings.md#bug-5--vscode-auto-revert-trap-operational).

### The LDS-relief refactor (Tests 71-74)

Moved `CoarseSmem.warpEmitMask` + `warpEmitPrefixSum` (~33 KB) out of
LDS into a per-block `CoarseGlobalScratch` allocation. Cut
`CR_COARSE_WARPS` 16→8 and `CR_FINE_MAX_WARPS` 20→12 to fit FineSmem
under the 32 KB budget. No-op smoke (Test 72) passes; real impls
(Tests 73-75) still crash. The bug is not just LDS pressure.

### Toolchain upgrade (Tests 80+)

Upgraded torch to 2.10.0+rocm7.0 (HIP 7.0.51831). Failure mode changed
from `Memory access fault by GPU node-1` (system reboot territory) to
`Cuda error: 719[hipStreamSynchronize(stream);]` (clean process exit).
Tests 83-85 enabled the rocm7 register-count diagnostic and revealed
**`regsPerThread=202-230`** for `rasterKernel` even with reduced warps.
Working hypothesis: register pressure is forcing `coarseBlocks=1`,
launch geometry exceeds resources, kernel fails to schedule.

setupKernel's kernarg is 12 bytes (matching `(ptr, int)`). rasterKernel's
is **272 bytes**. The 260-byte gap is implicit kernargs the compiler had
to add — including a hostcall buffer pointer.

### The actual trigger: printf in coarseRasterImpl

CoarseRaster.inl has 5 `printf` calls at lines 762, 781, 806, 849, 861.
These were added in Test 42 as OOB diagnostic instrumentation
(`[OOB-A]` through `[OOB-E]`) and have never actually fired —
Test 42 itself concluded "no [OOB-*] messages printed".

But the compiler must emit the device-side printf machinery whether
or not the branches fire. Searching the rasterKernel body in the
disassembly:

```
__ockl_printf_begin           ×N   per printf site
__ockl_hostcall_preview       ×N
__ockl_printf_append_string_n ×N
__ockl_printf_append_args     ×many   per format arg
```

setupKernel has zero `__ockl_*` references; rasterKernel has dozens.
The 5 dead-code printfs are the source of:

1. **+260 byte kernarg** (hostcall buffer + implicit args).
2. **+33 VGPRs** vs the comparable setupKernel (202 vs 169).
3. **+inlined hostcall control flow** through ~30 basic blocks
   (`.LBB1_158`, `.LBB1_265`, ...) keeping live values around for
   buffer-pointer + atomic counter management.

This explains:
- Why every "real impl" test since Test 42 crashed regardless of LDS
  size, dispatch order, sync barrier strategy, etc.
- Why the failure mode is `hipErrorLaunchOutOfResources` (719) on
  rocm7 — kernarg + VGPR + LDS combined hits some launch budget the
  scheduler enforces.
- Why Test 82 (no-op coarse with marker) passed — no-op skipped the
  printf paths' live-range bloat.
- Why all the workarounds in workarounds.md failed — they fought the
  symptom (crash address, dispatch count, sync ordering) rather than
  the cause.

### Remaining content of CoarseRaster.inl after the printfs

The bounds-check logic (clamp `segIdx` to a valid range) is real and
should stay. Only the `printf` calls are diagnostic and can be gated
behind a compile-time flag.

## Final resolution (end of day)

**Bug 6 — `triHeader[i].misc` OOB on RDNA3 — RESOLVED.**

Tests 91-130 produced a wrong hypothesis ("currPtr OOB / register
pressure"). Test 123 was the breakthrough — moving the early `return;`
to BEFORE the `triHeader` read at line 320 made the kernel pass.

Tests 124-126 confirmed the actual fault site: `triHeader[i].misc`
returns uninitialized garbage (e.g., `4138327560 = 0xF6A4_18B8` for
`triIdx=0`) for ~7% of active threads on RDNA3. The original NVIDIA
code assumes triangleSetup writes a valid `.misc` for every entry that
ends up in `binSegData`; on AMD that invariant breaks.

Fix: bounds-check both `triHeader[]` reads in `coarseRasterImpl` and
the `getTriangle` helper + per-fragment `triData` read in
`fineRasterImpl`. Threads with bad indices skip the triangle (coarse)
or emit a z-fail fragment (fine).
